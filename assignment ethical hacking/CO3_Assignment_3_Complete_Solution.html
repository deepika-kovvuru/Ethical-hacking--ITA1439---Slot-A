Decoupled Architecture: To capture the entire network attack surface without creating monolithic, unmaintainable data files, the joint team architected five decoupled, highly cohesive scan datasets. Detailed Specification of the Five Foundational Scan Datasets

  • 2. Ports Dataset (L4): Generated via &apos;nmap -sS -sU&apos;. Captures layer-4 transport states across TCP and UDP protocols, recording port numbers, protocol families, connection states, and scan drop reasons.

Column Name Data Type Constraints Default Security Analytics Description

  • Composite Keying: Enforcing composite primary key (host_ip, port_number, protocol) prevents duplicate observations while supporting services bound to both TCP and UDP on the same port.

Q1 – Individual Verification &amp; Faculty Defense Preparation

Defense Governance: In compliance with the SIMATS assessment guidelines, both candidates prepared exhaustive oral defense arguments and formal proofs for faculty cross-examination, demonstrating complete theoretical and implementation mastery of their respective components.

Student A Oral Defense: Host &amp; Port Schema Normalization

  • Defense of 1NF CSV over JSON: While JSON handles nested data, it incurs severe processing overhead in pure POSIX shell pipelines. First Normal Form (1NF) tabular CSV allows direct stream manipulation using coreutils (awk, cut, sort) without requiring external heavy JSON runtimes.
  • Handling Protocol Collisions: In modern networks, identical port numbers host completely different services under TCP and UDP (e.g., DNS port 53 TCP vs UDP). Keying solely on (host_ip, port_number) causes catastrophic primary key collisions.
  • Handling Port 0 Edge Cases: Port 0 is reserved under RFC 793 and RFC 768. The Ports schema strictly enforces a check constraint (port_number BETWEEN 1 AND 65535). Port 0 anomalies in scanner output indicate OS fingerprinters or raw packet craft artifacts.

Student B Oral Defense: Service Relationships &amp; Multi-OS Architecture

  • Resolving Schema Polymorphism: Attempting to store Windows SIDs, Android build tags, and Java RMI stubs in a single denormalized table results in a matrix with &gt;90% null values. The multi-entity relational schema eliminates sparsity while preserving domain-specific fidelity.
  • Handling Missing Service Banners: Network timeouts frequently cause banners to drop during high-speed scans. The relational design treats the Services table as an optional extension of the Ports table, ensuring ports are never lost even if banner grabbing fails.
  • Shell Pipeline Portability: By relying strictly on POSIX standard coreutils (awk, sort, comm, grep -E) rather than shell-specific extensions, the verification pipelines execute identically across Debian, Ubuntu, Kali, and Alpine containers.

Q3 – Joint Conclusion: Theoretical Limits of Automated Cleaning

Joint Conclusion Prompt: Joint Team Prompt: &apos;Why is automated scan-data cleaning alone insufficient to guarantee the accuracy of an assessment&apos;s findings?&apos;

Collaborative Theoretical Defense &amp; Architectural Analysis

Core Thesis: While automated shell scripts excel at rapid lexical filtering, integer range enforcement, and string normalization, relying solely on automated cleaning introduces profound risks in penetration testing. The pair identified four insurmountable limitations of pure automation.

  • 1. Contextual Blindness to Defensive Deception: Enterprise firewalls, Web Application Firewalls (WAFs), and intrusion deception platforms (honeypots) intentionally manipulate network packets. For example, a Honeyd honeypot will return SYN-ACK responses on all 65,535 TCP ports. An automated cleaning script would validate these records as 100% syntactically correct &apos;open&apos; ports, flooding the assessment report with thousands of phantom services.
  • 2. Non-Standard Service &amp; Protocol Tunneling: Sophisticated attackers and administrators frequently bind services to deceptive ports (e.g., running OpenSSH on port 443 to bypass egress filters, or hosting an HTTP command-and-control server on port 53). Automated scripts relying on static lookup tables or default port heuristics will misclassify or discard these anomalous banners, blinding analysts to the most critical attack paths.
  • 3. Routing Asymmetry &amp; Multi-Homed Endpoints: In corporate enterprise networks, core servers are frequently multi-homed (interfacing internal LANs, storage VLANs, and management networks). Probing the same machine across multiple interfaces can yield conflicting results (e.g., port 445 open on management VLAN, filtered on user LAN). Automated deduplication based purely on hostname or MAC address risks discarding valid access vectors.
  • 4. Destructive Filtering of Exploit Telemetry: Heuristic cleaning rules designed to strip &apos;malformed&apos; strings frequently discard active exploitation telemetry. Binary exploit payloads, SQL injection reflection banners, or corrupted buffer overflow responses will fail standard ASCII regex checks. An automated script would discard these lines as corrupted noise, silently destroying evidence of an active zero-day vulnerability.

Proposed Enterprise Triaging Model: Human-in-the-Loop (HITL)

Best Practice Framework: To reconcile speed with absolute forensic accuracy, the team recommends an architectural model where the automated pipeline functions strictly as a triage pre-filter. Syntactically clean records flow immediately into automated vulnerability scanners, while all quarantined, duplicate, or unmapped telemetry is routed to human security analysts for manual review.
